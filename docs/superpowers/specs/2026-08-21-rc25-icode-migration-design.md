# rc.25 迁移 0.13.2-icode 定制功能设计

## 1. 背景与基线

本次迁移以官方 `v1.0.0-rc.25` 为唯一代码基线，将
`v0.13.2-icode` 中尚未被上游吸收的定制能力迁移到新版。

仓库盘点结果：

- 官方 `v0.13.2` 是 `v1.0.0-rc.25` 的祖先；
- `v0.13.2-icode` 相对官方 `v0.13.2` 增加 64 个提交；
- 其中 4 个补丁已经被 `v1.0.0-rc.25` 等价吸收，不重复迁移；
- 其余约 60 个提交需要按业务语义重新实现；
- 定制差异覆盖额度池、自动充值、LDAP、账号归并、统计、权限策略、
  用户管理、日志和前端等模块。

新版前端已经迁移到 React、TypeScript、TanStack Router 和 feature 目录体系，
后端的认证、session、计费和后台任务也已演进。因此本次不合并旧分支，
也不批量 cherry-pick，而是按功能域迁移并逐域验证。

## 2. 目标与非目标

### 2.1 目标

- 迁移全部仍有效的 `0.13.2-icode` 定制功能；
- 直接接管现有 `0.13.2-icode` 生产数据库并原地升级；
- 保留现有用户、额度池、余额、管理员关系、日志和配置；
- 适配 `rc.25` 的认证、session、计费、后台任务和前端架构；
- 同时支持 SQLite、MySQL 和 PostgreSQL；
- 保持独立 ClickHouse 日志库下的统计能力；
- 为资金、迁移、权限和账号归并补齐并发与负向测试；
- 保留项目现有名称、组织标识、许可证和受保护元数据。

### 2.2 非目标

- 不把额度池改造成推理请求的直接资金来源；
- 不改变 `rc.25` 的钱包/订阅计费优先级和回退语义；
- 不恢复旧版 JSX 页面或引入旧 UI 兼容层；
- 不机械还原旧分支的提交历史；
- 不修改计费表达式语言或动态计费模型；
- 不引入与迁移无关的全局重构。

## 3. 总体迁移策略

采用“官方基线 + 功能域语义迁移”路线：

1. 从官方 `v1.0.0-rc.25` 建立迁移分支；
2. 建立旧提交到新实现的功能映射清单；
3. 先完成数据库兼容与升级测试；
4. 再迁移资金事务、权限和后台任务；
5. 随后迁移 LDAP、OAuth、统计和管理策略；
6. 最后按新版组件体系原生重写前端；
7. 在三种数据库和生产库副本上进行升级演练。

每个旧定制项最终必须标记为以下状态之一：

- 已迁移；
- 已由 `rc.25` 等价替代；
- 因新版架构变化而采用新的等价实现；
- 经用户明确同意后排除。

## 4. 数据库兼容设计

### 4.1 基本原则

迁移必须是增量、幂等且非破坏性的：

- 保留现有 `quota_pools`；
- 保留现有 `quota_pool_admins`；
- 保留现有 `quota_pool_transactions`；
- 保留 `users.quota_pool_id`、`users.ldap_id` 和 `users.department`；
- 保持表名、字段名、额度单位、池类型和流水类型不变；
- 不删除、不重建、不清空现有业务表；
- 不批量覆盖池余额、配置、成员归属或管理员关系；
- 所有迁移步骤允许重复执行。

三个额度池模型加入 `rc.25` 的 GORM 迁移流程。新增字段必须提供兼容旧数据的
默认值，禁止依赖单一数据库方言。

### 4.2 系统额度池初始化

系统默认池和新用户池只在缺失时创建。已有记录只执行必要的结构校验，不能：

- 重置余额或累计额度；
- 覆盖用户配置；
- 迁移已有成员；
- 触发自动首充；
- 触发余额回收；
- 触发月度充值。

初始化必须在 schema 迁移和数据不变量检查完成后执行。

### 4.3 旧库升级顺序

升级流程为：

```text
0.13.2-icode 生产库副本
  -> rc.25 官方迁移
  -> icode 兼容迁移
  -> 数据不变量检查
  -> API、充值和登录冒烟测试
  -> 启动后台充值任务
```

迁移前后必须比较：

- 用户数量、用户余额、累计用量；
- 用户额度池归属；
- 额度池余额、累计额度和配置；
- 池管理员关系和等级；
- 历史资金流水条数和金额；
- LDAP 标识和部门信息；
- 关键系统配置。

### 4.4 回滚

- 上线前必须制作数据库快照；
- 在生产副本上验证升级和应用回滚；
- 数据库变化尽量保持旧版可忽略的新增表或新增列；
- 对 `rc.25` 自身包含的字段类型变化，以数据库快照作为最终回滚保障；
- 数据检查通过前不得启动自动充值和月度补齐任务。

## 5. 角色与权限兼容

旧库可能存在 `role = 2` 的额度池超级管理员。迁移后继续保留：

```go
RoleQuotaPoolSuperAdmin = 2
```

权限约束：

- `role = 2` 可以作为普通登录用户通过认证；
- 不能因数值比较进入系统 Admin 或 Root API；
- 额度池路由显式允许池超级管理员、系统 Admin、Root 或池管理员关系；
- `authz.RequirePermission` 必须显式适配，不能只依赖 `role >= minRole`；
- 池 v1/v2 权限继续由 `quota_pool_admins` 表表达；
- 所有管理路由均增加 `role = 2` 的越权负向测试。

前端不重复推导复杂权限。额度池响应提供 capability，例如：

```json
{
  "can_edit": true,
  "can_refill": false,
  "can_manage_members": true,
  "can_manage_v1_admins": true,
  "can_manage_v2_admins": false
}
```

## 6. 后端模块边界

按 Router、Controller、Service、Model 分层迁移：

```text
Router
  -> Controller: 参数解析和响应映射
  -> Service: 业务规则、事务和权限后的动作编排
  -> Model: 模型、查询和原子持久化操作
```

建议职责：

- `model/quota_pool*.go`：模型、查询、统计和原子数据操作；
- `service/quota_pool*.go`：创建、配置、迁移、资金和管理员规则；
- `service/auto_recharge*.go`：自动充值和月度充值任务；
- `controller/quota_pool*.go`：管理端、自助端、资金、成员和统计接口；
- `setting/operation_setting`：自动充值配置；
- `router/api-router.go`：额度池和 LDAP 路由。

不直接复制旧版两个超大文件。文件按单一职责拆分，并遵守仓库的函数、文件、
嵌套和复杂度上限。

## 7. 额度池资金设计

### 7.1 资金边界

额度池只负责向用户钱包发放额度，不直接支付 API 请求：

- 请求消费仍通过 `BillingSession`；
- 资金来源仍是用户钱包或订阅；
- 不修改 `FundingSource`；
- 非默认池成员钱包不足时提示联系池管理员；
- `subscription_first`、`wallet_first` 等新版回退行为保持不变。

### 7.2 充值事务

人工充值、自动充值和首次充值复用同一个 Service 入口：

```text
校验用户和额度池
  -> 开启事务
  -> 锁定用户和额度池
  -> 条件扣减池余额
  -> 增加用户钱包余额
  -> 写额度池资金流水
  -> 提交事务
  -> 写用户日志和管理审计
```

规则：

- 池扣减、用户增加和池资金流水必须在同一事务；
- 使用 `quota >= amount` 条件更新，禁止先读后写；
- 余额不足时整笔失败，不做部分发放；
- MySQL/PostgreSQL 使用行锁；
- SQLite 使用事务加条件更新；
- 多池操作按池 ID 固定顺序加锁；
- 资金流水失败时回滚资金事务；
- 事务提交后的用户日志失败只记录系统错误，不回滚资金。

### 7.3 成员迁移和余额回收

- 正余额离开有限非默认池时退回旧池；
- 负余额迁移时清零，但不调整池余额；
- 默认池余额不回收；
- 用户余额清零后更新 `quota_pool_id`；
- 同事务移除旧池管理员关系；
- 进入目标非默认池后再尝试自动首充；
- 首充失败不撤销迁移，只返回 warning；
- 迁移主事务失败时不得留下半迁移状态。

### 7.4 管理员直接调额

- Root 只能直接增加、减少或覆盖默认池用户余额；
- 非默认池成员只能通过额度池充值和回收接口调整；
- 系统 Admin 可以执行固定金额充值，但不能任意覆盖余额；
- 充值不受目标用户角色等级限制；
- 普通用户更新接口不能通过提交 `quota` 修改余额。

## 8. 自动充值和月度充值

### 8.1 自动充值任务

复用 `rc.25` 的 `SystemTask` 数据库租约机制：

- Master 节点负责调度；
- 数据库租约保证多实例只有一个执行者；
- 租约过期后允许其他执行者接管；
- 每轮先执行月度池充值，再扫描用户；
- 单个用户失败不阻塞后续用户；
- 记录成功数、失败数和跳过原因统计。

系统关闭额度池功能时，默认池用户仍沿用系统自动充值逻辑。

### 8.2 次数统计兼容

- 新日志写入 `recharge_source=auto`、`quota_pool_id`、金额和操作者；
- 查询同时识别旧版内容前缀和新版结构化字段；
- 人工充值不计入周/月自动充值次数；
- 自动首充值计入次数限制。

### 8.3 月度固定充值和补齐

月度任务在同一事务内：

1. 重新读取并锁定额度池；
2. 检查状态、执行日期和 `last_refill_month`；
3. 固定模式增加配置金额；
4. 补齐模式增加 `max(target - current, 0)`；
5. 更新 `quota`、`base_quota` 和执行月份；
6. 实际金额大于零时写资金流水；
7. 金额为零时只更新月份。

更新条件必须包含旧执行月份，确保并发任务最多成功一次。

## 9. LDAP 设计

LDAP 登录接入 `rc.25` 的统一认证链路：

- LDAP bind 成功后调用统一 `setupLogin`；
- 登录方式记录为 `ldap`；
- 继续执行 session 限制、`auth_version`、刷新令牌、2FA 和登录审计；
- 密码只用于当次 bind，不记录、不保存。

账号识别顺序：

1. 精确匹配 `ldap_id`；
2. 按规范化邮箱匹配未删除用户；
3. 未匹配且允许注册时创建普通用户；
4. 命中已删除账号时拒绝创建；
5. 同步展示名、部门、邮箱和 LDAP ID，不覆盖角色、状态、分组、额度或权限。

管理员同步使用查询、签名候选项、明确选择、验签和写入的两阶段流程。
LDAP 设置包括地址、Base DN、Search DN、Search Password、过滤器、UID、Scope
和超时；读取设置时必须掩码 Search Password。

## 10. OAuth 邮箱归并

账号解析顺序：

1. provider user ID；
2. `rc.25` 已支持的 legacy ID；
3. 规范化邮箱；
4. 创建新账号。

邮箱归并规则：

- 只在 Provider 能证明邮箱已验证时自动归并；
- 内置 Provider 传递邮箱验证状态；
- 无法证明邮箱可信的自定义 Provider 不自动归并；
- 此时提示用户先登录现有账号后手工绑定；
- provider ID 冲突、账号已删除或已有不同绑定时拒绝；
- 账号归并和 OAuth binding 在同一事务完成；
- 只更新 binding 字段，不写回完整用户快照；
- 成功后使用户缓存失效。

## 11. 统计、日志和审计

### 11.1 统计范围

- 系统 Top 用户：按时间、模型和额度消耗排序；
- 自动充值榜：次数、总金额、周限制和稳定并列排序；
- 额度池统计：成员消耗、模型分类、充值和资金流向。

### 11.2 独立日志库

- 先在 `LOG_DB` 聚合用户 ID 和消费数据；
- 再从主数据库批量补充用户和额度池信息；
- 禁止跨数据库 JOIN；
- SQLite、MySQL、PostgreSQL 使用统一语义；
- ClickHouse 日志库提供对应聚合实现；
- 查询限制时间范围、分页和最大 `limit`；
- 隐藏金额或占比为零的模型项；
- 主指标相同时按次指标和用户 ID 稳定排序。

### 11.3 日志和审计

- 消费日志和错误日志始终记录请求 IP；
- 不记录 LDAP 密码、OAuth token 或 Search Password；
- 额度池资金流水与管理审计分开；
- 管理员、池管理员和后台任务均记录来源；
- 后台任务使用 `operator_id=0`，同时记录任务 ID 和节点标识。

## 13. API 错误设计

Service 层使用稳定领域错误，Controller 统一映射 HTTP 状态、错误码和翻译：

- `QUOTA_POOL_DISABLED`；
- `QUOTA_POOL_NOT_FOUND`；
- `QUOTA_POOL_INSUFFICIENT`；
- `QUOTA_POOL_MEMBER_MISMATCH`；
- `QUOTA_POOL_REFILL_LIMITED`；
- `QUOTA_POOL_PERMISSION_DENIED`；
- `LDAP_AUTH_FAILED`；
- `LDAP_IDENTITY_CONFLICT`；
- `OAUTH_EMAIL_UNVERIFIED`。

成员迁移成功但首充失败时返回成功并携带结构化 warning：

```json
{
  "success": true,
  "data": {
    "member": {},
    "initial_recharge": {
      "success": false,
      "reason": "QUOTA_POOL_INSUFFICIENT"
    }
  }
}
```

客户端不能看到数据库错误、LDAP 内部错误和 OAuth token 内容。
